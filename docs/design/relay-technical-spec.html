Technical specification — draft

Relay

AI-assisted live presentation software for churches. Combines OBS-style capture, ATEM-style multi-output switching (reframed), and ProPresenter-style templated display, driven by real-time scripture detection tuned for African-language services. Built to interoperate with existing gear, not replace it.

01

Overview & positioning

Three existing tool categories currently cover live church production: OBS (capture, scene compositing, recording, free), ATEM (hardware video switching, one program bus from many inputs), and ProPresenter (templated lyrics, stage display, timers). Pewbeam is a newer, funded competitor that adds real-time AI scripture detection on top of a presentation layer, with paying churches in 30 countries and a stated roadmap toward a full presentation suite.

Relay's wedge is not to rebuild all four categories to parity. It's the combination of AI content intelligence (what should be on screen, right now, based on what's actually being said) with independent multi-screen templating (each screen gets its own style from the same decision) — and doing both with African-language speech understanding as a first-class target, not an afterthought.

Explicit design stance
Relay sits above the existing AV chain, not in place of it. It talks to OBS, ATEM, and ProPresenter over NDI, HDMI, and the local network — it does not try to replace what any of them already do well.
02

Goals & non-goals

v1 success criteria

  • ≥90% correct verse ID on direct quotes, ≥75% on paraphrase, in under 3 seconds (p50), in real live-room audio
  • Wrong-verse rate under 5% of AI triggers, with an always-visible one-tap operator override
  • A full service runs 100% offline, zero internet dependency
  • 3+ simultaneous output channels, each with its own template, under 100ms cross-channel sync drift
  • At least one output channel confirmed running on a $50 Raspberry Pi kiosk client
  • NDI output confirmed ingestible by both OBS and vMix
  • Runs smoothly on an 8GB RAM Windows laptop
  • Survives 3 consecutive live Sunday services with zero crashes, and the projection team reports it beats manual control

Explicit non-goals (v1)

  • Not a recording / scene-compositing replacement for OBS.
  • Not building native SDI hardware output (Blackmagic DeckLink-class integration) — see §9.
  • Not a general-purpose AI assistant — scope is strictly live-service content routing.
  • Not attempting song-lyric/setlist detection in v1 — scripture detection only; worship-set control remains manual (may be a v2 track).

04

AI detection pipeline

  1. Chunking: audio → 200–500ms overlapping chunks → voice-activity-detection gate, skip silence.
  2. Streaming STT: local whisper.cpp-class model → rolling partial + final transcript window, with per-chunk language identification (required for English/local-language code-switching, very common in African preaching).
  3. Direct pattern match: regex over the transcript for <book> <chapter>:<verse> shapes, multilingual book-name alias tables per priority language, phonetic-ASR-error tolerance (e.g. "John free sixteen" → John 3:16).
  4. Semantic match: embed the rolling window, vector-similarity search against a pre-embedded verse corpus, return top-k candidates with a confidence score. Catches paraphrase and topical reference.
  5. Context memory: track "current passage" state. If the preacher already anchored on Psalm 23 and later says only "verse 4," resolve against the last active book/chapter rather than requiring a fresh full reference. Not something Pewbeam advertises publicly — a deliberate differentiator.
  6. Confidence gating, two-tier: high confidence (exact regex match, or semantic score above threshold) auto-fires to the program. Mid confidence surfaces as a one-tap "suggested" chip in the operator UI without touching output on its own. Low confidence is dropped silently.
  7. Debounce: ~4–6 second cooldown on repeat auto-fire of the same verse, immediately overridden by any new explicit direct-quote match.
  8. Operator override: first-class, top-of-UI control, one tap — never a buried escape hatch.
Open / needs real data
Exact confidence-score thresholds are not something to guess in a spec — they need tuning against a real transcript + verse corpus once sample sermon audio exists.
05

Output channels & template system

A channel is a configured destination. A template is a layout + style + data-binding definition that any channel can be assigned. The same content event (e.g. "John 3:16 fired") renders differently per channel because each channel points at a different template — not because the content pipeline treats them differently.

Stage display and lobby-screen templates follow the same shape with different region sets (e.g. stage adds a timer region; lobby adds a next_event region) — same engine, different JSON.

Community datasets to evaluate for fine-tuning: Masakhane (African NLP research), Mozilla Common Voice. Code-switching handling (English mixed mid-sentence with a local language) is treated as a first-class requirement, not an edge case — it's the normal case in target-market preaching.

09

Integration & interoperability

NDI

Free SDK, cross-platform. Relay is an NDI source; OBS, ATEM (NDI-enabled models), vMix, and ProPresenter can all ingest it directly.

HDMI

Not a special integration — a borderless fullscreen window on whichever display is physically connected via HDMI. Cheap, no hardware SDK needed.

SDI — explicitly out of scope

True SDI I/O requires dedicated capture/output hardware (Blackmagic DeckLink-class) and a C++ SDK — high engineering cost for narrow reach. Decision: not building it. Anyone with SDI-based gear already owns hardware (an ATEM, or a standalone converter) that accepts NDI or HDMI input and re-outputs SDI. Relay's NDI/HDMI output preserves full SDI-setup compatibility without owning the SDI hardware problem.

Glossary

Output channel
An independently-styled destination (a screen, a stream, a kiosk) that receives its own template rendering of the same underlying content decision. Deliberately not modeled as an ATEM-style single program bus.
Content router
The subsystem that decides what each output channel shows, and when, based on AI detections and manual cues.
Render target
How a channel's template is actually output — native window (HDMI), headless NDI encode, or networked browser client (kiosk).
Direct match
Regex-based detection of an explicit spoken reference, e.g. "John 3:16."
Semantic match
Embedding + vector-similarity detection of a paraphrased or topical scripture reference.
Context memory
Tracking the "current passage" so a bare "verse 4" resolves against the last-referenced book/chapter.
Confidence gating
Two-tier trigger logic — high confidence auto-fires, mid confidence surfaces as an operator-confirmable suggestion, low confidence is dropped.
